# 배치를 안 키우면 어떤 GPU를 사도 decode는 빨라지지 않는다

*Hands-On LLM Serving and Optimization 스터디 3주차 정리*

---

2주차 글 끝에 계산 하나를 숙제로 남겼다. decode가 memory-bound라는 건 설명으로 알겠지만 그걸 숫자로 말하려면 스텝마다 읽는 바이트를 대역폭으로 나눠봐야 한다고 적었다. 5장이 그 도구를 준다. 산술 강도(arithmetic intensity)와 루프라인 모델이다.

## 두 숫자를 비교하는 것

산술 강도는 연산량을 데이터 이동량으로 나눈 값이다. 단위는 FLOPS/B.

```
arithmetic intensity = FLOPS / bytes moved
```

칩에도 같은 비율이 있다. 최대 연산 성능을 메모리 대역폭으로 나누면 그 칩의 손익분기점이 나온다. 교재는 L40S로 계산한다. FP16 362 TFLOPS를 864 GB/s로 나누면 약 419 FLOPS/B.

워크로드의 산술 강도가 이 값보다 낮으면 연산 유닛이 아무리 좋아도 다 못 쓴다. 데이터가 도착하기를 기다리는 시간이 길어서다. 높으면 반대로 대역폭이 남고 연산이 병목이 된다.

## 행렬곱 하나로 환원된다

트랜스포머 연산의 대부분은 행렬곱이다. `[M,K] × [K,N]` 행렬곱의 산술 강도는 정의대로 세면 이렇게 된다.

```
연산량 = 2 × M × N × K
데이터 = 2 × (M×K + K×N + M×N)
AI     = M×N×K / (M×K + K×N + M×N)
```

LLM에서는 M이 시퀀스 길이 s, K와 N이 히든 차원 h가 된다. prefill은 프롬프트 토큰을 한꺼번에 밀어넣으니 s가 크다. decode는 토큰을 하나씩 만드니 **s = 1로 고정**이다.

s=1을 넣으면 분자가 h²이고 분모가 2h + h²다. AI는 h/(h+2)가 된다. h가 몇이든 1에 붙는다. 419와 비교할 값이 아니다.

decode가 memory-bound인 건 구현이 나빠서도, 캐시가 커서도 아니다. 행렬 모양이 그렇게 생겼다.

## 그럼 배치는 얼마나 키워야 하나

여기서부터는 교재에 없어서 직접 계산했다. 배치 크기 B를 넣으면 decode의 행렬은 `[B,h] × [h,h]`가 된다. 위 공식에 그대로 대입된다.

```
AI(B, h) = B×h / (2B + h)
```

B를 무한히 키우면 이 값은 **h/2로 수렴한다.** 배치로 올릴 수 있는 상한이 히든 차원의 절반이라는 뜻이다.

1주차에 뜯어봤던 Qwen2.5-0.5B는 h가 896이다. 상한이 448이다. L40S 손익분기점 419를 넘기는 한다. 다만 실제로 419에 도달하려면 배치가 6,473이어야 한다. KV 캐시만으로도 카드가 터지는 크기다.

h=4096짜리 모델은 사정이 다르다. 상한이 2048이고, 419를 넘는 데 배치 527이면 된다.

같은 배치 512를 걸어도 결과가 갈린다.

| h | B=1 | B=128 | B=512 | 상한(B→∞) |
|---|---|---|---|---|
| 896 | 1.0 | 99.6 | 238.9 | 448 |
| 4096 | 1.0 | 120.5 | 409.6 | 2048 |

작은 모델은 배치를 아무리 키워도 그 칩의 연산력을 다 못 쓴다. 큰 모델을 서빙할 때보다 GPU가 더 놀고 있다는 얘기다. 작은 모델이 서빙하기 쉽다고 생각했다. 처리량 효율만 보면 반대다.

## 배치 B는 시퀀스 길이 s와 수학적으로 같은 자리다

공식을 다시 보면 decode의 B와 prefill의 s가 정확히 같은 위치에 들어간다. `AI(B,h)`와 `AI(s,h)`가 같은 식이다.

배치 512로 decode를 돌리는 것과 512 토큰짜리 프롬프트를 prefill하는 것이 GPU 입장에서 같은 모양의 행렬곱이다. 실제로 h=4096, s=512일 때 교재 표의 prefill 값이 409.60인데, 내가 계산한 B=512 decode 값도 409.60이다.

배칭은 흔히 "요청을 모아 처리량을 올린다"로만 설명된다. 하는 일은 **decode를 prefill 모양으로 되돌리는 것**에 가깝다. 2주차에 봤던 continuous batching이 왜 그렇게 중요한 기법인지가 여기서 숫자로 나온다.

## 안 풀린 것

상한 h/2는 이상적인 행렬곱 기준이다. 실제로는 어텐션 부분이 KV 캐시를 읽어야 해서 데이터 이동량이 더 늘어난다. 그만큼 산술 강도는 더 떨어질 것이다. KV 캐시를 분모에 넣은 식으로 다시 세우면 상한이 얼마나 내려가는지는 아직 안 해봤다.

그리고 6장의 기법들(FlashAttention, 양자화, prefix caching)을 이 그림에 놓고 각각 분자를 줄이는 쪽인지 분모를 줄이는 쪽인지 나눠보면 정리가 될 것 같다. 아직 그렇게 읽지는 못했다.
