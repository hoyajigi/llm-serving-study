# 캐시 적중률은 올랐는데 꼬리 지연이 5배 더 늘었다

*Hands-On LLM Serving and Optimization 스터디 7주차 정리*

---

마지막 주차는 llm-d다. vLLM 파드 앞에 Envoy Gateway와 EPP(Endpoint Picker)를 세우고 요청을 어느 파드로 보낼지 KV 캐시 상태를 보고 정하는 구조다.

실습에서 같은 워크로드를 두 경로로 돌려 짝지어 비교한 결과가 나온다. 하나는 쿠버네티스 Service로 직접 때리는 라운드로빈, 하나는 Gateway를 경유하는 precise prefix-cache-aware 라우팅이다.

| 지표 | 직접 호출 | Gateway 경유 |
|---|---|---|
| Prefix 캐시 적중률 | 63.9% (40,896/64,005) | **68.75%** (44,000/64,005) |
| 파드 간 쿼리 분산 | 42 / 58 | 62 / 38 |
| Mean TTFT | 59~66 ms | 67~69 ms |
| P99 TTFT | 113~151 ms | 148~173 ms |
| Throughput | ~3.9~4.1 req/s | ~4.0~4.1 req/s |

적중률은 4.85%p 올랐다. 그런데 TTFT는 평균도 P99도 나빠졌다.

## "게이트웨이 홉 때문"이라는 설명이 안 맞는다

실습 정리는 TTFT 증가를 Gateway→EPP 홉이 붙으면서 생긴 고정 오버헤드로 해석한다. 그럴듯한데, 같은 문서의 다른 절에 그 오버헤드를 실제로 잰 숫자가 있다. Jaeger 분산 트레이싱 플레임그래프다.

```
total 450.44ms → gateway.request(100%) → vllm-decode: llm_request(99.46%, 448.01ms)
→ EPP 오버헤드는 전체 요청의 0.54%
```

450.44 × 0.0054 = **2.43ms**다.

이제 증가폭을 구간 중앙값으로 놓고 맞춰보면 이렇게 된다.

```
Mean TTFT  62.5 → 68.0    +5.5 ms
P99  TTFT  132.0 → 160.5  +28.5 ms
```

2.43ms는 평균 증가분의 44%는 설명한다. **그런데 P99 증가분의 8.5%밖에 설명하지 못한다.**

여기가 핵심이다. 고정 오버헤드는 분포 전체를 같은 양만큼 밀어야 한다. 모든 요청이 똑같이 2.43ms를 더 내니까 평균도 2.43ms, P99도 2.43ms 올라야 맞다. 실제로는 평균이 5.5ms 오를 때 꼬리가 28.5ms 올랐다. **꼬리가 평균보다 5.18배 더 늘었다.**

분포가 평행 이동한 게 아니라 옆으로 벌어졌다. 그러면 원인은 고정비가 아니라 부하에 따라 변하는 비용이다.

## 부하에 비례하는 비용이 하나 더 있다

정밀 방식의 구성을 보면 답이 나온다.

> **정밀(Precise) 방식** — 프롬프트를 vLLM의 `/v1/completions/render` HTTP 엔드포인트로 보내 정확한 토큰 ID 획득

EPP에는 토크나이저가 없다. 그래서 캐시 점수를 매기려면 **요청마다 vLLM에 토큰화 왕복을 한 번 더 건다.** 근사(Approximate) 방식은 문자-토큰 비율로 때려맞히므로 이 왕복이 없다. 정밀 방식만 있다.

로그에도 그대로 찍힌다.

```
10.42.0.17:33942  → "POST /v1/chat/completions/render"    (EPP 파드가 보낸 토큰화 요청)
10.42.0.225:39450 → "POST /v1/chat/completions"           (Gateway가 보낸 실제 추론)
```

실습 정리는 이 두 줄을 "서로 다른 두 흐름이니 다른 파드에 떨어져도 문제없다"고 설명하고 넘어간다. 토큰화 결과가 파드마다 같으니 정확성 면에서는 맞는 말이다. 하지만 **비용 면에서는 문제가 된다.** 토큰화 요청도 결국 추론용 vLLM 파드가 받아서 처리한다. 실제 추론과 같은 서버, 같은 큐다.

그래서 정밀 라우팅을 켜면 vLLM이 받는 HTTP 요청 수가 두 배가 된다. 그중 절반은 토큰만 세고 버리는 요청이다. 이 경합은 한가할 때는 안 보이고 몰릴 때만 보인다. 정확히 꼬리에서 나타나는 모양이다.

플레임그래프의 0.54%는 **EPP 자기 자신이 쓴 시간**이다. EPP가 유발했지만 다른 프로세스가 치른 비용은 그 스팬 밖에 있다. 측정한 구간이 비용의 전부가 아니었다.

## 6주차에 겪은 것과 같은 함정이다

지난주에 llmperf의 `inter_token_latency_s`가 토큰 사이 간격이 아니라 E2E를 토큰 수로 나눈 값이라는 걸 검산으로 잡았다. 이름이 가리키는 것과 실제로 재는 것이 달랐다.

이번엔 범위가 달랐다. 0.54%라는 숫자 자체는 정확하다. 다만 그게 덮는 구간이 "라우팅 때문에 늘어난 시간"이 아니라 "EPP 프로세스 안에서 흐른 시간"이었다. 요약 숫자 하나를 받을 때 그게 무엇을 재는지보다 **어디까지 재는지**를 먼저 물어야 한다는 쪽에 가깝다.

## 어피니티는 공짜가 아니다

파드 분산이 42/58에서 62/38로 바뀌었다. 캐시 어피니티가 걸렸다는 증거이고 실습 정리가 그렇게 읽은 것도 맞다. 다만 이건 동시에 **의도적으로 부하를 한쪽으로 몰았다**는 뜻이기도 하다. 바쁜 파드 기준으로 트래픽이 1.069배가 됐다.

3주차에 배치 크기가 처리량의 레버라는 걸 계산했고 6주차에는 Trainium에서 그 레버가 컴파일 시점에 굳는 걸 봤다. 라우팅은 그 레버를 파드별로 다르게 당기는 일이다. 캐시를 맞히려고 한 파드에 몰아주면 그 파드의 유효 배치가 커지고, 배치가 커지면 개별 요청의 대기가 늘어난다. 처리량은 유지되는데 지연의 꼬리가 두꺼워지는 게 자연스러운 결과다.

실제로 처리량은 양쪽이 같았다. 바뀐 건 같은 처리량을 어떤 지연 분포로 냈느냐다.

## 그래서 이 규모에서는 손해였다

파드 2개에 Qwen3-0.6B다. TPOT가 15ms라 캐시 미스로 다시 계산해봐야 아끼는 시간이 얼마 안 된다. 반면 토큰화 왕복은 프롬프트 길이에 비례해서 꼬박꼬박 붙는다.

실습 정리도 "파드 수가 많고 모델이 커서 cache-miss 재계산 비용이 큰 환경에서 이점이 뚜렷할 것"이라고 적었는데, 위 분해는 그 조건을 조금 더 구체적으로 만들어준다. 손익분기는 **캐시 히트로 아끼는 prefill 시간이 토큰화 왕복 한 번을 넘어서는 지점**이다. 파드 수가 아니라 프롬프트 길이와 모델 크기가 먼저 걸린다.

파드 수는 그 다음 문제다. 라운드로빈이 우연히 캐시를 맞힐 확률이 파드 N개에서 1/N로 떨어지니, N이 커질수록 어피니티가 가져오는 적중률 이득이 커진다. 여기서는 N=2라 그 확률이 이미 50%였다.

## 아직 안 해본 것

근사 방식으로 바꿔서 같은 벤치마크를 돌리면 토큰화 왕복이 사라진다. 위 해석이 맞다면 적중률은 조금 떨어지고 P99는 직접 호출 수준으로 돌아와야 한다. 이 한 번의 비교가 "꼬리 증가가 토큰화 경합 때문"이라는 가설을 바로 판정한다. 지금은 숫자를 교차해서 고정비로 설명이 안 된다는 것까지만 보인 상태다.

vLLM 파드가 받은 요청을 종류별로 세어보는 것도 필요하다. `/render`와 `/v1/chat/completions`의 비율이 1:1인지, 스트리밍이나 재시도 때문에 더 붙는지는 로그를 세어봐야 안다. 1:1이 아니라면 위 추정이 과소평가일 수 있다.
