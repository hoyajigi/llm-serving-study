# vLLM을 붙였는데 동시 요청이 순차로 처리된다

*Hands-On LLM Serving and Optimization 스터디 2주차 정리*

---

3장 실습은 FastAPI로 모델 서빙 서비스를 밑바닥부터 만든다. 큐잉, 배칭, 프로세스 격리, 스트리밍을 각각 최소 형태로 구현해본 뒤 마지막에 `/generate_vllm` 엔드포인트를 붙여 vLLM으로 갈아탄다.

프롬프트 3개를 리스트로 넣으면 잘 돈다. 로그에 `Processed prompts: 3/3` 이 찍히고 배열 3개가 돌아온다.

그런데 요청을 두 개로 나눠서 동시에 보내면 두 요청이 하나의 배치로 합쳐지지 않는다. 순차로 처리된다. 연속 배칭이 vLLM의 간판 기능인데 그게 동작하지 않는다.

## 원인은 엔진 바깥에 있다

`vllm.LLM.generate()`는 동기 함수다. 이걸 async 핸들러 안에서 `await` 없이 호출하면 그동안 이벤트 루프가 통째로 막힌다. Uvicorn은 기본적으로 단일 이벤트 루프로 돈다. 첫 요청이 GPU에서 돌아오기 전까지 두 번째 요청은 핸들러 진입조차 못 한다.

엔진 입장에서는 요청이 한 번에 하나씩만 들어온다. 배칭할 대상이 애초에 없는 셈.

여기서 헷갈렸던 부분을 정리하면, 배칭에는 층이 두 개 있다.

- 한 요청 안의 배칭 — 프롬프트 리스트를 한 번에 넘기는 것. `generate(["a","b","c"])`. 이건 동기 API로도 된다
- 요청 사이의 배칭 — 서로 다른 HTTP 요청에서 온 프롬프트를 같은 실행 배치에 섞는 것. 연속 배칭이 말하는 게 이쪽이다

두 번째가 되려면 엔진이 여러 요청을 동시에 들고 있어야 한다. 요청을 엔진에 넣어주는 쪽(웹 서버, 큐, 스케줄러)이 직렬화돼 있으면 엔진이 아무리 똑똑해도 한 번에 하나만 본다. 그래서 해결책이 vLLM 설정이 아니라 `AsyncLLMEngine`으로 바꾸고 진입 경로를 비동기로 여는 쪽이다.

## 교재의 아키텍처가 왜 그렇게 쪼개져 있는지

3장은 단일 모델 서빙을 API 서버, 워크로드 매니저, 모델 익스큐터, 모델 워커로 나눈다. 그리고 이걸 다시 세 층으로 묶는다. 인프라 관리(로드밸런서, 복제, 헬스체크), 서빙 프론트엔드(인증, 검증, 배칭, 레이트 리밋), 서빙 백엔드(실제 추론, 별도 프로세스).

처음 봤을 때는 교과서적인 계층 분리로 읽혔다. 위의 현상을 보고 나니 백엔드를 별도 프로세스로 두라는 대목이 다르게 읽힌다.

GPU 작업은 한 번 시작하면 그 스레드를 오래 붙잡는다. CPU 쪽 일(HTTP 파싱, 인증, 검증, 큐 관리)과 같은 실행 컨텍스트에 있으면, GPU가 도는 동안 들어오는 요청을 받을 수가 없다. 요청을 못 받으면 큐에 쌓이지 않고, 큐가 비면 배칭할 게 없다.

프로세스를 나누는 걸 장애 격리나 코드 정리 쪽 이야기로 읽었다. 큐를 계속 채우기 위한 조건에 더 가깝다. 워크로드 매니저가 별도 컴포넌트로 있는 이유도 같은 자리에 있다.

실습 코드에서는 이 분리가 실제로 프로세스 단위로 나타난다. `ps auxf`를 찍으면 부모(uvicorn+FastAPI) 아래로 자식이 둘 붙는다. 부모는 GPU를 전혀 쓰지 않고 모델 워커(788MB)와 vLLM 엔진 코어가 각각 별도 PID로 GPU를 잡는다. vLLM 0.9의 V1 아키텍처는 TP=1로 GPU 한 장만 써도 EngineCore를 별도 프로세스로 띄운다.

## 0.24GiB 모델이 13.7GB를 쓴다

같은 실습에서 걸린 것 하나 더. 데모 모델은 `facebook/opt-125m`이고 가중치는 0.24GiB인데, EngineCore 프로세스가 GPU 메모리를 13.7GB 잡는다.

`gpu_memory_utilization` 기본값이 0.9다. vLLM은 가중치를 올린 뒤 남는 공간을 KV 캐시로 미리 통째로 예약한다. 로그에 잡힌 KV 캐시 크기가 356,816 토큰이다.

1주차에 토큰당 KV 캐시 바이트를 세어봤을 때 캐시 크기가 곧 동시 처리 가능한 요청 수라는 결론이 나왔다. vLLM은 그 계산을 기동 시점에 해서 자리를 먼저 잡아둔다. `nvidia-smi`에 찍힌 13.7GB 중 모델 가중치는 0.24GiB이고 나머지는 캐시 예약이다.

## 4장에서 걸린 것: 지표를 못 믿는 이유

4장은 지연시간을 셋으로 쪼갠다. E2E, TTFT(첫 토큰까지), ITL(토큰 사이 간격). 그리고 `E2E = TTFT + ITL × (N-1)` 로 묶는다.

쓸모 있는 건 유스케이스별로 뭘 봐야 하는지가 갈린다는 부분이다. 챗봇은 TTFT가 체감을 지배한다. 출력이 길면 ITL 쪽이 지배한다. 그런데 에이전트 워크플로우는 다르다. 다음 단계가 이전 단계의 완성된 전체 출력을 입력으로 받으니 첫 토큰이 빨리 나오는 게 아무 의미가 없다. 각 단계의 E2E가 다음 단계를 그대로 블로킹한다. 체인이 길어질수록 이게 누적된다.

처리량 쪽에서는 TPS가 부풀려질 수 있다는 경고가 있다. 입력을 짧게 자르면 프리필 부담이 줄어 TPS가 올라간다. 배치 안의 입출력 길이를 균일하게 맞춰도 올라간다. 둘 다 모델이나 엔진 속도와는 무관한 조작인데 숫자는 좋아진다.

TPS가 출력 토큰만 센다는 것도 이번에 정확히 알았다. 입력 토큰은 안 들어가고 입출력 합산도 아니다. 같은 워크로드를 입력 포함으로 계산한 숫자와 비교하면 애초에 다른 걸 비교하는 셈이 된다.

## 아직 안 해본 것

동기 API를 `AsyncLLMEngine`으로 바꿨을 때 동시 요청이 실제로 한 배치에 합쳐지는지, 그때 TTFT와 ITL이 어떻게 갈리는지는 직접 안 재봤다. 순차 처리될 때와 배치로 합쳐질 때 두 지표가 반대 방향으로 움직일 것 같은데(배치에 묶이면 개별 요청의 TTFT는 늘고 전체 TPS는 오르는 쪽), 확인은 못 했다.

`gpu_memory_utilization`을 낮추면 KV 캐시가 줄고 동시 처리 가능한 요청 수도 줄어든다. 그 관계가 선형인지, 어느 지점부터 급격히 무너지는지는 재봐야 안다.
